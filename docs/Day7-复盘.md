## 一、今天解决的核心问题：账不平

**今天的开头，我们看到了这张表**：

| 账户 | 当前余额 | 账单净额 | 对得上吗 |
|---|---|---|---|
| 微信钱包 | 1000.00 | +477.01 | ❌ |
| 支付宝 | 2000.00 | -25.50 | ❌ |
| 中国银行 | 3000.00 | +8000.00 | ❌ |

**原因**：记了 6 笔账，但账户余额一动都没动。

**为什么？** 因为之前 `BillService.create()` 只做了**一件事**——往 `bill` 表插记录。
它**根本没碰 `account` 表**。

而"记一笔账"在业务上其实是**两件事**：

```
① 往 bill 表插一条账单记录
② 把 account 表的余额改掉（支出减、收入加）
```

**今天就是把第 ② 步补上，并且保证①②"同生共死"。**

## 二、两个实验，让你亲眼看到"为什么必须用事务"

这是今天最有价值的部分。我们**故意注入了一个故障**，然后对比了三种情况。

### 实验前基准

```
账单 7 条    支付宝 2000.00
```

### 实验 1：故障发生在"第 2 步之后"（**没有事务**）

```
写入账单 ✓   扣款 ✓   然后出事 ✗
```

| 结果 | |
|---|---|
| 账单条数 | 7 → **8** |
| 支付宝余额 | 2000 → **1900**（扣了） |
| 用户看到的响应 | `{"code":1,"msg":"系统繁忙，请稍后再试"}` |

**问题**：用户以为失败了，其实**钱已经扣了、账也记了**。
如果他重试一次 → **重复扣款**。

> 这类 bug 在真实系统里非常常见，尤其在网络不稳定的时候
> （请求发出去了，但响应没回来，用户以为失败又点了一次）。

### 实验 2：故障发生在"两步中间"（**没有事务**）

```
写入账单 ✓   出事 ✗   扣款没执行
```

| 结果 | |
|---|---|
| 账单条数 | 7 → **8** |
| 支付宝余额 | 2000 → **2000**（一分没扣） |
| 用户看到的响应 | `{"code":1,"msg":"系统繁忙，请稍后再试"}` |

**这才是最典型的"账不平"**：

> 数据库里多了一笔 100 元的支出记录，**但钱根本没收**。
> 而且这条"幽灵账单"会永远留在那里，没人知道它没扣过钱。

**这个错误会一直累积**。记 10 笔这样的账，账面上就多出几千块的"假支出"。

### 实验 3：同样的故障，但**加上了事务**

```
@Transactional
```

| 结果 | |
|---|---|
| 账单条数 | 7 → **7**（没变！） |
| 支付宝余额 | 2000 → **2000**（没变） |
| 用户看到的响应 | `{"code":1,"msg":"系统繁忙，请稍后再试"}` |

**数据库完全干净——第 ① 步的写入被自动撤销了。**

**三个实验并排看：**

| | 账单条数 | 余额 | 结果 |
|---|---|---|---|
| 实验1（无事务，故障在后） | 7 → **8** | 2000 → 1900 | 用户以为失败，其实成功了 |
| 实验2（无事务，故障在中） | 7 → **8** | 2000（未扣） | **账不平：有账单没扣钱** |
| **实验3（有事务）** | 7 → **7** | 2000 | ✅ **干净回滚** |

## 三、什么是事务（用一句话记住）

> **事务 = 把多个数据库操作打包成一个"不可分割的整体"：要么全成功，要么全失败。**

生活比喻：**转账**。

```
从 A 账户扣 1000 元  +  给 B 账户加 1000 元
```

这两步**必须一起完成**。如果只扣了 A 的钱、没加到 B 的账户上，
那 1000 块就凭空消失了 —— **没人能接受**。

**所以我们记账也一样**：
- 账单记录 + 余额变动，必须一起生效或一起撤销

### 代码上有多简单

```java
@Transactional          // ← 就加这一行
public void create(Bill bill) {
    // ... 各种校验 ...
    billMapper.insert(bill);                              // 第①步
    accountMapper.updateBalance(bill.getAccountId(), delta); // 第②步
}
```

**一行注解，Spring 自动帮你处理回滚。** 这就是框架的价值。

## 四、事务的四个特性：ACID（面试常问）

| 特性 | 含义 | 今天体会到的 |
|---|---|---|
| **A 原子性**（Atomicity） | 要么全做，要么全不做 | ✅ **今天重点就是这个** |
| **C 一致性**（Consistency） | 数据从一个正确状态变到另一个正确状态 | ✅ 有事务后账就平了 |
| **I 隔离性**（Isolation） | 并发的事务之间互不干扰 | 还没遇到，以后做并发测试时讲 |
| **D 持久性**（Durability） | 提交后就不会丢（就算断电） | 数据库默认保证 |

## 五、@Transactional 三个必须知道的细节（容易踩坑）

### ① 默认只对"运行时异常"回滚

| 异常类型 | 默认行为 | 例子 |
|---|---|---|
| `RuntimeException` 及其子类 | ✅ **回滚** | `IllegalArgumentException`（我们的校验异常） |
| 受检异常（`Exception` 的其他子类） | ❌ **不回滚** | `IOException`、`SQLException` |

**我们项目刚好没问题**——所有业务校验抛的都是 `IllegalArgumentException`，
它是 `RuntimeException` 的子类。

**但这是个经典坑**：如果哪天你换成抛出受检异常，事务会**静默失效**——
看起来"事务加了但没起作用"，非常难查。

**要让它对受检异常也回滚**，得显式声明：
```java
@Transactional(rollbackFor = Exception.class)
```

### ② 方法必须是 `public`

Spring 的事务是靠**代理对象**实现的（跟 MyBatis 给 Mapper 生成代理是同一个套路）：

```
你为什么能调 service.create()？
    因为 Spring 给你的 Service 包了一层"代理对象"：
    进入方法前 → 开启事务
    方法执行完 → 提交
    方法抛异常 → 回滚
```

**如果方法不是 public，代理拦不住，事务就失效了。**

### ③ 【进阶坑，先知道有这回事】同类内部调用不走代理

```java
@Service
public class FooService {
    public void methodA() {
        this.methodB();      // ❌ 这样调用，methodB 上的 @Transactional 无效！
    }

    @Transactional
    public void methodB() { ... }
}
```

**为什么？** 因为 `this.methodB()` 是**直接调用自己**，
绕过了那个包在外面的代理对象，Spring 根本没机会插进去开事务。

**正确做法**是把 methodB 移到另一个类里，或者注入自己（`@Autowired FooService self`）。
**这个坑等你以后遇到再说，现在记住"@Transactional 靠代理生效"就够了。**

### ④ 事务注解该加在哪里？

```
Controller  ❌ 粒度太粗（会把查询操作也算进事务，浪费资源）
Service     ✅ 正合适（一次完整业务操作的边界就在这里）
Mapper      ❌ 太细（那里的每个方法只是一小步，不是完整业务）
```

**判断方法**：问自己"这几个数据库操作，是不是必须同生共死？"
是 → 把它们所在的那个 Service 方法加上 `@Transactional`。

## 六、今天第二个技术点：增量更新（避免"丢失更新"）

改余额有两种写法：

### 写法 A（错的）：查出来 → Java 里算 → 写回去

```java
Account a = findById(1);              // 查到 1000
a.setBalance(a.getBalance() - 35);    // Java 里算 = 965
update(a);                            // 写回 965
```

### 写法 B（对的，我们用的）：让数据库自己算

```sql
UPDATE account SET balance = balance + #{delta} WHERE id = #{id}
```

### 为什么 A 会出错？—— 并发场景演示

假设两个人几乎同时从微信钱包支出：

| 时刻 | 用户甲 | 用户乙 | 数据库余额 |
|---|---|---|---|
| T1 | 查到余额 = 1000 | | 1000 |
| T2 | | 查到余额 = 1000 | 1000 |
| T3 | 算好 1000-35 = 965 | | 1000 |
| T4 | | 算好 1000-20 = 980 | 1000 |
| T5 | 写入 965 | | 965 |
| T6 | | 写入 980 | **980** |

**结果**：总共支出了 55 元，但余额只从 1000 变成 980（少扣了 35）。
**用户甲那笔支出凭空消失了。**

这个经典问题叫「**丢失更新**」（Lost Update）。

### 写法 B 为什么没问题？

因为**"算这一步"交给了数据库**。数据库执行 `UPDATE` 时会**对这一行加锁**，
第二个人必须等第一个人做完才能执行：

| 时刻 | 数据库执行 | 余额 |
|---|---|---|
| T5 | `balance = 1000 + (-35)` | 965 |
| T6 | `balance = 965 + (-20)` | **945** ← 正确！ |

### 一句话记住

> **"算钱"这件事，能在数据库里做，就别拿到 Java 里做。**
> 因为数据库有锁机制保证顺序，而 Java 代码之间是没有的。

（这是你以后会听说的"悲观锁 / 乐观锁"话题的入口。）

## 七、今天第三个技术点：`@Param`（多参数必须用）

```java
int updateBalance(@Param("id") Long id, @Param("delta") BigDecimal delta);
```

**为什么必须加 `@Param`？**

MyBatis 面对**多个参数**时，无法自动判断 XML 里的 `#{id}` 该对应哪个参数
（它看到的只是没有名字的第 1 个、第 2 个参数）。

**不加会报**：
```
Parameter 'id' not found. Available parameters are [arg0, arg1, param1, param2]
```
（这个报错其实已经把答案告诉你了——它说只有 `arg0`/`arg1` 可用。）

**对比之前的方法**：`findById(Long id)` 只有一个参数，
所以 `#{id}` 怎么写都能取到值。**但一旦有 2 个以上参数，`@Param` 就是必须的。**

> 顺便：即使项目配置了保留参数名（我们项目就是，Maven 编译带 `-parameters`），
> `@Param` 依然是**推荐写法**——它让代码不依赖编译配置，任何环境下都稳。

## 八、今天新增的校验：余额不足拦截

```java
if (bill.getType() == Bill.TYPE_EXPENSE
        && account.getBalance().compareTo(bill.getAmount()) < 0) {
    throw new IllegalArgumentException(
        "账户余额不足，当前余额 ¥" + account.getBalance() + "，本次需要 ¥" + bill.getAmount());
}
```

**两个设计考虑**：

**① 为什么只检查支出，不检查收入？**
收入是往口袋里加钱，加多少都不会"超"。

**② 为什么提示里要带上具体金额？**
```
"账户余额不足"                                    ← 用户不知道差多少，还得自己去翻
"账户余额不足，当前余额 ¥965.00，本次需要 ¥99999"   ← 一眼就知道差多少 ✓
```
**错误提示的目标是"让用户知道下一步该怎么做"**，只说"失败了"等于没说。

## 十、错误对照表（Day7 新增）

| 现象 | 原因 | 怎么办 |
|---|---|---|
| 记了账但余额不变 | Service 里没调 `updateBalance` | 补上第②步（今天做的正是这个） |
| 有账单但钱没扣（账不平） | 没有事务，第②步失败但第①步没撤销 | 加 `@Transactional` |
| 用户重试导致重复扣款 | 用户以为失败其实成功 | 加事务 + 幂等设计（以后讲） |
| `@Transactional` 加了却没生效 | 方法不是 `public`，或同类内部调用 | 检查方法修饰符；避免 `this.xxx()` |
| 抛受检异常时没回滚 | 默认只回滚 `RuntimeException` | 写 `@Transactional(rollbackFor = Exception.class)` |
| `Parameter 'id' not found` | 多参数没用 `@Param` | 给每个参数加 `@Param("名字")` |
| 并发时余额少扣 | 用了"查出来算再写回" | 改用 `SET balance = balance + ?` |
| 记账后页面余额没变 | 只刷新了账单列表，忘了刷新账户 | 两个列表都要重新加载 |

## 十二、⚠️ 一个遗留事项：历史账单还没"对账"

**现在的数据是"不平"的**，因为 Day7 之前的账单**都没有联动余额**：

| 账户 | 当前余额 | 账单净额 | 差额 |
|---|---|---|---|
| 微信钱包 | 1000.00 | +477.01 | 差 522.99 |
| 支付宝 | 2000.00 | -25.50 | 差 25.50 |
| 中国银行 | 3000.00 | +8000.00 | 差 8000.00 |

**这不是 bug，是历史数据的问题**：

> 那 6 笔账单是在"还没有余额联动功能"的时候记的。
> 现在功能有了，但**历史账单不会自动追溯**。

**真实世界里这是个很常见的任务，叫「数据迁移」或「对账」**——
新功能上线后，需要用一次性脚本把历史数据补齐。

**两个选择**（下次可以一起处理）：
- **A. 对账**：把余额调整成"初始余额 + 账单净额"，让账变平
- **B. 不管它**：反正只影响这 6 条测试数据，继续往下做功能

我倾向 **A**，因为以后做"统计报表"时，账不平会很让人困惑。

## 十四、明天预告（Day8）

**做"统计"——把记的账变成有用的信息。**

记账的目的是**看清钱花在哪了**，所以下一步自然是：
- **按分类统计**：这个月餐饮花了多少、交通花了多少
- **按月份统计**：近几个月的收支趋势
- **`GROUP BY` 聚合查询** —— SQL 里最有威力的功能之一
- **ECharts 图表** —— 把数字变成饼图和折线图

**这里会用到前几天学的东西**：
- 连表查询（Day6 学的 JOIN）
- 聚合函数（`SUM`、`COUNT`、`GROUP BY`）
- 而且是**只读操作**，不会碰事务的复杂性

**另外要注意**：做统计时，那个"历史账不平"的问题会显现出来
（因为统计要么基于账单、要么基于余额，两者不一致会让人困惑）——
所以我们可能顺便把对账做了。
