## 二、核心概念：两道防线，缺一不可

```
用户点按钮
   ↓
【前端校验】—— 体验层：让正常用户少犯错，提示友好
   ↓  （但可以被绕过！）
【后端校验】—— 安全层：真正拦住所有请求，这是数据的最后一道门
   ↓
数据库
```

| | 前端校验 | 后端校验 |
|---|---|---|
| 目的 | **体验**：用户填错时立刻提示，不用等一次网络往返 | **安全**：保证进库的数据一定合法 |
| 位置 | 浏览器里（用户电脑上） | 服务器上（你控制的机器） |
| **能不能被绕过** | **能，而且很容易** | 不能 |
| 谁写 | `rules`（Element Plus 表单规则） | Service 里的 if 判断 |

### 为什么前端校验挡不住人

**因为前端代码跑在用户的电脑上。** 用户想改就改、想绕就绕。今天你亲手试过的那行代码：

```js
fetch('/api/account/create', {
  method: 'POST',
  headers: {'Content-Type': 'application/json'},
  body: JSON.stringify({name:'', balance:1})
})
```

**这一行，跟点按钮发出的请求一模一样** —— 同一个接口、同一条 SQL。
唯一的区别是：它**跳过了页面上的那段校验代码**。

### 一条必须刻进脑子的原则

> **任何来自客户端的数据都是不可信的。**
> 哪怕前端已经校验过三遍，后端也必须自己再校验一遍。

（你以后会看到这个原则的其他面孔：SQL 注入、XSS 攻击、越权访问……
本质都是同一件事——**不要相信客户端**。）

## 三、第二件事：为什么异常要"统一翻译"

### 问题：出错时的格式和成功时不一样

| 情况 | 返回格式 |
|---|---|
| **成功**（我们自己写的） | `{"code":0, "msg":"ok", "data":null}` |
| **出错**（Spring 默认的） | `{"timestamp":"...","status":500,"error":"Internal Server Error","path":"..."}` |

**两个格式完全不一样，后果有三个**：

1. **前端读不懂** —— 它按 `code/msg/data` 写的代码，遇到这个格式只能走 catch 分支，显示一句没用的"网络错误"，用户根本不知道错在哪
2. **泄露技术细节** —— 时间戳、请求路径、甚至类名和 SQL，攻击者能从中收集情报
3. **体验割裂** —— 成功时的友好提示和失败时的陌生格式，像两个不同的系统

### 解决：`@RestControllerAdvice`（全局异常处理器）

```java
@RestControllerAdvice
public class GlobalExceptionHandler {

    // 负责"业务校验失败"这类异常
    @ExceptionHandler(IllegalArgumentException.class)
    public Result<Void> handleIllegalArgument(IllegalArgumentException e) {
        log.warn("业务校验未通过：{}", e.getMessage());
        return Result.fail(e.getMessage());   // ← 翻译成统一格式
    }

    // 兜底：所有没人认领的异常
    @ExceptionHandler(Exception.class)
    public Result<Void> handleException(Exception e) {
        log.error("系统异常", e);              // 详细内容只写日志
        return Result.fail("系统繁忙，请稍后再试");  // 前端只给笼统一句
    }
}
```

### 它凭什么能"抓住"异常？（工作机制）

```
Controller 抛出异常
      ↓
【Spring 拦截】← 因为有 @RestControllerAdvice 存在
      ↓
按异常类型匹配 @ExceptionHandler，规则是"就近原则"：
   IllegalArgumentException  →  匹配 handleIllegalArgument（更具体）
   其他任何 Exception        →  匹配 handleException（兜底）
      ↓
用方法的返回值（Result 对象）作为响应，转成 JSON 返回
```

**最大的好处**：写一次，**全项目所有接口都生效**。
不用在每个 Controller 里写 try-catch —— 如果你见过那种"每个方法都包一层 try-catch"的代码，
就知道这个注解有多省事。

### 一个重要的设计选择：HTTP 200 + 业务 code

我们这个项目选了：**HTTP 状态码永远是 200，业务错误靠 `code` 区分。**

| 风格 | 做法 | 好处 | 谁在用 |
|---|---|---|---|
| **A（我们用的）** | HTTP 200 + `code≠0` | 前端只需判断一处（`code`），逻辑简单不易漏 | 国内多数项目 |
| B | HTTP 400 + `code≠0` | 符合 HTTP 语义，浏览器/网关/监控能自动识别为失败 | 部分团队、开放 API |

**两种都能用，关键是全项目统一。** 等以后你接监控报警系统时，可能会理解为什么有些团队选 B。

## 四、今天三个新知识点

### 1. `trim()` —— 拦"看起来是空的"字符串

```java
if (account.getName() == null || account.getName().trim().isEmpty()) {
```

**为什么要 `trim()`？** 因为 `"     "`（一串空格）在肉眼看来是空的，
但用 `isEmpty()` 判断会返回 `false`（它确实有内容，只是全是空格）。

`trim()` 的作用是**去掉首尾空白字符**，于是：

```
"     ".trim()  →  ""      →  isEmpty() 返回 true，被拦住 ✓
```

**如果没有 `trim()`，攻击④（纯空格名字）就能蒙混过关。**
这类"看起来没问题其实有问题"的输入，是校验里最容易被漏掉的一类。

### 2. `BigDecimal` 比较大小不能用 `<` `>`，要用 `compareTo()`

```java
if (account.getBalance().compareTo(BigDecimal.ZERO) < 0) {
```

| 写法 | 结果 |
|---|---|
| `balance < 0` | ❌ 编译不过（BigDecimal 是对象，不是数字） |
| `balance == BigDecimal.ZERO` | ❌ **能编译，但结果永远错**——它比的是"是不是同一个对象"，不是"数值是否相等" |
| `balance.compareTo(BigDecimal.ZERO) < 0` | ✅ 正确。`compareTo` 返回：负数=小于，0=等于，正数=大于 |

**这是 `BigDecimal` 最经典的坑之一**，几乎每个用 Java 处理金额的人都踩过。

### 3. 日志级别怎么选：WARN 还是 ERROR

看我们怎么用的：

| 场景 | 用什么级别 | 为什么 |
|---|---|---|
| **用户输入不对**（校验失败） | `WARN` | 这是**预期内**的正常情况，用户填错了而已，不是系统故障 |
| **系统故障**（空指针、连不上数据库） | `ERROR` | 这才是真正需要你排查的问题 |

**为什么这个区分很重要？**

想象一下：如果你把所有问题都记成 `ERROR`，那么日志里 99% 都是
"用户填错名字"这种噪音，真正的系统故障就被淹没了 —— **出大问题时你根本发现不了。**

> 经验法则：**WARN = "这个情况有点问题，但我知道为什么"**；
> **ERROR = "出事了，需要人去看"**。

## 五、今天的实验记录（一手资料，很有价值）

### 修复前：4 次攻击，3 次成功

| 攻击 | 请求内容 | 响应 | 结果 |
|---|---|---|---|
| ① 空名字 | `{"name":"","balance":100}` | `{"code":0,"msg":"ok"}` | 💀 **脏数据进库** |
| ② 名字为 null | `{"balance":100}` | `{"timestamp":...,"status":500,...}` | ⚠️ 报错但**格式乱** |
| ③ 负余额 | `{"name":"恶意账户","balance":-99999}` | `{"code":0,"msg":"ok"}` | 💀 **负余额进库** |
| ④ 纯空格 | `{"name":"     ","balance":50}` | `{"code":0,"msg":"ok"}` | 💀 **脏数据进库** |

**数据库被污染成**（加上你自己在控制台加的）：
```
13 条记录，其中 6 条名字空白，1 条余额 -99999
```

### 修复后：5 次攻击，全部失败

| 攻击 | 响应 | 结果 |
|---|---|---|
| ① 空名字 | `{"code":1,"msg":"账户名称不能为空"}` | ✅ **拦住了** |
| ② 名字为 null | `{"code":1,"msg":"账户名称不能为空"}` | ✅ **拦住了，且格式统一了** |
| ③ 负余额 | `{"code":1,"msg":"余额不能为负数"}` | ✅ **拦住了** |
| ④ 纯空格 | `{"code":1,"msg":"账户名称不能为空"}` | ✅ **拦住了**（`trim()` 的功劳） |
| ⑤ 60 字超长 | `{"code":1,"msg":"账户名称不能超过 50 个字"}` | ✅ **拦住了** |

**同时验证**：边界值正好 50 字 → **正常通过**（校验不能"宁可错杀"）

**⚠️ 对比②修前修后**：这是今天最有说服力的一处对比
- 修前：`{"timestamp":"...","status":500,"error":"Internal Server Error"}`
- 修后：`{"code":1,"msg":"账户名称不能为空"}`

**同一个错误，修后前端终于能读懂并显示人话提示了。**

## 七、错误对照表（今天新增）

| 现象 | 原因 | 怎么办 |
|---|---|---|
| 脏数据能进库 | 后端没校验 | **后端必须自己校验**，不能只靠前端 |
| 出错时返回格式和成功时不一样 | 没有全局异常处理 | 加 `@RestControllerAdvice` |
| 前端只显示"网络错误"，看不到具体原因 | 后端返回格式前端读不懂 | 统一成 `{code,msg,data}` |
| 纯空格名字通过了校验 | 忘了 `trim()` | `name.trim().isEmpty()` |
| `balance < 0` 编译报错 | BigDecimal 是对象 | 用 `compareTo()` |
| `balance == BigDecimal.ZERO` 结果总是不对 | 比的是对象引用不是数值 | 用 `compareTo() == 0` |
| 后端堆栈直接吐给前端 | 没做兜底处理 | `@ExceptionHandler(Exception.class)` 拦下，详细内容只写日志 |
| 日志里全是 ERROR 找不到重点 | 级别用得不对 | 用户输入错误用 WARN，系统故障才用 ERROR |

## 九、今天你很关键的一个提问

你问过："**我不太清楚这种脏数据是怎么个注入法，因为你本来就有我电脑文件读写的权限，
我不知道和普通的添加数据有什么区别**"

**这个问题问得非常好**，它暴露了一个真实存在的认知盲区。答案有三层：

1. **我没用到文件权限** —— 我走的是**网络请求**（curl），跟你点按钮走的是同一条路
2. **技术上完全没区别** —— 同一个接口、同一条 SQL、同一个数据库
3. **唯一的区别在"路上"** —— 你的浏览器会先跑一遍页面校验，curl 不跑

**能想到"他凭什么能做到"这件事，说明你在主动思考，而不是被动接受。**
这个习惯比记住任何结论都值钱 —— Day3 你也是靠它抓到了我给错的 ID。
