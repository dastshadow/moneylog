## 二、新概念：`vo` —— 查询结果的容器

**这是今天最需要理解的一个设计判断。**

前几天的实体类（`Account`、`Bill`）都是**表的映射**：表的一行 ↔ 对象的一个实例。

但今天的统计结果长这样：

```
category | total  | billCount
餐饮     | 35.00  | 1
交通     | 55.51  | 2
```

**`bill` 表里根本没有 `total` 这一列！** 它是"好几行账单合并算出来的一个数"。

所以不能用 `Bill` 装 —— 装不下。得给"这个形状"单独建一个类。

**判断方法（以后设计接口天天要用）：**

| 结果的形状                 | 用什么装                         |
| --------------------- | ---------------------------- |
| = **一张表的一行**          | `entity`（如 `Account`、`Bill`） |
| = **多行算出来的汇总 / 拼接结果** | **`vo`**（如 `CategoryStats`）  |

> `vo` 是行业叫法（View Object）。别的项目可能叫 `dto`（Data Transfer Object）、  
> `bo`（Business Object）—— **是同一类东西**，看到别的名字不用懵。

今天建了三个：

```
vo/CategoryStats.java   分类统计（category / total / billCount）
vo/MonthlyStats.java    月度统计（month / expense / income）
vo/SummaryStats.java    月度汇总（总支出 / 总收入 / 结余 / 笔数）
```

## 三、今天的技术核心：`GROUP BY` 聚合

### 从"一行进一行出"到"多行进一行出"

在这之前，我们所有查询都是：

```sql
SELECT * FROM bill        → 有几条账单就返回几行
```

`GROUP BY` 做的事是"**先分组，再对每组算一个数**"：

```
原始数据：               GROUP BY category 之后：
  餐饮  35.00              餐饮组：[35.00, 50.00]
  餐饮  50.00     →        交通组：[25.50, 30.01]
  交通  25.50              购物组：[88.00]
  交通  30.01
  购物  88.00

然后 SUM(amount) 对每组求和：
  餐饮  85.00
  交通  55.51
  购物  88.00
```

### 一条必须记住的规则

> **`SELECT` 后面的列，除了被聚合函数（`SUM`/`COUNT`/`AVG`...）包起来的，  
> 其他每一个都必须出现在 `GROUP BY` 里。**

**为什么？** 分组之后一组有多行，`category` 每组只有一个值（好办），  
但 `amount` 每组有多个值 —— 直接 `SELECT amount` 数据库不知道该给哪个。

```sql
SELECT category, amount FROM bill GROUP BY category          -- ❌ 报错
SELECT category, SUM(amount) FROM bill GROUP BY category     -- ✓ 正确
```

### 用到的两个聚合函数

| 函数            | 作用         | 返回类型对应       |
| ------------- | ---------- | ------------ |
| `SUM(amount)` | 把这一组的金额加起来 | `BigDecimal` |
| `COUNT(*)`    | 数这一组有几条记录  | `Integer`    |

两个一起用，前端就能显示"餐饮 ¥85.00（3 笔）"。

## 四、今天的第二个核心技巧：条件聚合

**需求**：每个月，支出多少、收入多少 —— 两个数字要在同一行里。

```sql
SUM(CASE WHEN type = 1 THEN amount ELSE 0 END) AS expense,
SUM(CASE WHEN type = 2 THEN amount ELSE 0 END) AS income
```

**思路**：不看别的，只看"符合条件的那部分"：

```
假设10月有三条：
  type=1  35.00   → 第一个SUM取 35.00，第二个取 0
  type=1  25.50   → 第一个SUM取 25.50，第二个取 0
  type=2 500.00   → 第一个SUM取 0，    第二个取 500.00
  ───────────────────────────────────────────────
  结果：expense = 60.50，income = 500.00  ✓
```

**这个技巧叫「条件聚合」，做报表时天天用。** 它的价值是：

> **一次扫描数据，同时算出多个维度的统计** —— 比查好几次快得多。

（另一种做法是查两条 SQL 再在 Java 里按月份合并，麻烦且容易出错。）

## 五、`DATE_FORMAT` 和一个重要的性能预警

```sql
DATE_FORMAT(bill_date, '%Y-%m')
     '2026-10-11'  →  '2026-10'
     '2026-10-05'  →  '2026-10'    ← 同一个月，归到一组
```

**格式符号**：`%Y` 四位年、`%m` 两位月、`%d` 两位日（MySQL 的写法，Oracle 用 `TO_CHAR`）。

### ⚠️ 性能预警（今天埋个伏笔）

筛某个月有两种写法：

| 写法      | SQL                                                            | 能用索引吗               |
| ------- | -------------------------------------------------------------- | ------------------- |
| A（我们在用） | `WHERE DATE_FORMAT(bill_date,'%Y-%m') = '2026-10'`             | ❌ **用不上**（对列做了函数运算） |
| B       | `WHERE bill_date >= '2026-10-01' AND bill_date < '2026-11-01'` | ✅ 能走索引              |

**写法 A 对 `bill_date` 这一列做了函数运算**，数据库就没法用 Day6 建的那个  
`idx_bill_date` 索引了，只能逐行算 —— 表大了会明显变慢。

**为什么现在还用 A？** 因为可读性好、也不容易写错月份边界。

**以后数据量大了真遇到慢查询，再改成 B。** 这条优化原则叫  
「**避免在索引列上做运算**」，是个高频面试点 —— 先记住有这回事。

## 六、`NULL` 陷阱：`SUM` 和 `COUNT` 在空集合上的区别

**这个坑必须记住，因为它是"静默错误"。**

如果某个月**一条账单都没有**：

| 函数         | 空集合时返回     | 为什么                      |
| ---------- | ---------- | ------------------------ |
| `SUM(...)` | **`NULL`** | "对空集合求和"数学上没有定义          |
| `COUNT(*)` | **`0`**    | "数有几行"，没有行就是 0 —— 意思是明确的 |

**不处理的后果**：

```
前端拿到 null → null.toFixed(2) 直接报错崩溃
              → 或者界面显示 "¥ null"
```

**解决**：`IFNULL(SUM(...), 0)` —— "如果是 NULL 就换成 0"。

**验证过**：查一个没有账单的月份（2026-01），返回的是

```json
{"totalExpense":0.00,"totalIncome":0.00,"balance":0.00,"billCount":0}
```

**干干净净，没有崩溃。**

> **通用原则：聚合函数遇到空集合会返回 NULL，  
> 返回值给前端之前，一定要在 SQL 或 Java 里兜成 0。**

## 七、今天终于用上了第三种传参方式：`@RequestParam`

到这里，三种传参方式集齐了：

| 参数放哪         | 例子                                     | 注解                  | 什么时候用   |
| ------------ | -------------------------------------- | ------------------- | ------- |
| **URL 问号后面** | `/stats/category?month=2026-10&type=1` | **`@RequestParam`** | 筛选条件    |
| **请求体里**     | `{"name":"中国银行"}`                      | `@RequestBody`      | 要提交的数据  |
| **URL 路径里**  | `/api/account/6`                       | `@PathVariable`     | 指向某一条记录 |

**判断口诀：**

- "**筛选用什么条件**" → 问号后面
- "**要提交/保存的数据**" → 请求体
- "**指向某一条具体记录**" → 路径里

所以：查列表、查统计（带筛选）用第一种；新增/修改用第二种；删单条、改单条用第三种。

> 小知识：`@RequestParam` 默认 `required = true`（必填）。  
> 不传时 Spring 直接返回 400 —— 这就是 Day5/6 讲的"HTTP 层面的问题用 4xx"。  
> 但我们也在 Service 里校验了并给出中文提示，这是"框架兜底 + 业务友好提示"的配合。

## 八、今天踩的真实坑：别名配置没覆盖新包

**启动直接失败了**，日志里是：

```
Could not resolve type alias 'CategoryStats'.
Cause: java.lang.ClassNotFoundException: Cannot find class: CategoryStats
```

**根因**：XML 里写 `resultType="CategoryStats"` 用的是"简写别名"，  
而别名机制只覆盖了 `entity` 包 —— 我新建的 `vo` 包**不在覆盖范围内**。

**修复**（`application.yml`）：

```yaml
# 改前
type-aliases-package: com.wuweiqiu.moneylog.entity
# 改后（多个包用英文逗号分隔，不能有空格）
type-aliases-package: com.wuweiqiu.moneylog.entity,com.wuweiqiu.moneylog.vo
```

**这是 Day1 讲过的"别名机制"第一次真正踩到。** 当时配了它只是为了让  
`resultType="Account"` 能简写；今天新建包才暴露出它的作用范围。

> **这类错误的特征很好认**：报错里出现 `Cannot find class: Xxx`，  
> 而那个类明明存在 —— 那就是"别名没配到"。  
> 两个解法：① 把它所在的包加进配置 ② 在 XML 里写完整包名。

## 九、今天还做了「组件拆分」

`App.vue` 已经涨到 600 行（账户 + 账单两套功能挤在一起）。今天的统计再塞进去就要破 800 了。

**所以新建了 `components/StatsPanel.vue`，App.vue 里只留三行：**

```vue
import StatsPanel from './components/StatsPanel.vue'
...
<el-tab-pane label="统计" name="stats">
  <StatsPanel />
</el-tab-pane>
```

**行数对比**：`App.vue` 534 行，`StatsPanel.vue` 381 行。

### 拆分的判断标准（不是"行数够了就拆"）

> **问自己："这块东西能不能独立地说清楚它是什么？"**
>
> - 能 → 它就是一个组件（例如"统计面板"）
> - 不能 → 说明还没想清楚，先待在原地

**不拆的代价**：

- 找一个变量要滚半天
- 改统计的样式，风险是碰到账户的代码
- 多人协作时大家挤在一个文件里改，冲突不断

### 子组件和父组件怎么配合？

这个组件**不接收父组件任何数据**（统计只按分类和月份，不需要账户信息）——  
这叫"无 props 组件"，自己管自己就够。

**如果以后需要**（比如"只统计某个账户"），就加一个 `props` 接收 `accountId`。  
**按需加，不要提前设计**。

## 十、前端另外两个值得记住的点

### 1. `Promise.all` —— 能并发就别排队

页面要拉 4 个接口。我不在 `await` 里一个个排队，而是：

```js
const [s, e, i, m] = await Promise.all([...4个请求...])
```

| 写法            | 总耗时            |
| ------------- | -------------- |
| 一个个 `await`   | = 四个请求耗时**之和** |
| `Promise.all` | ≈ **最慢那个**的耗时  |

**页面要拉多个接口时，能并发就并发** —— 用户等待时间直接砍掉大半。

### 2. ECharts 的两个必知细节

**① 数据格式要转换**  
后端给的是 `[{category, total, billCount}]`，而 ECharts 饼图要的是 `[{name, value}]`。  
这种"后端数据 → 图表要求格式"的转换是前端画图的日常。

**② 窗口大小变化时要手动 `resize()`**  
ECharts 画出来的是固定尺寸的 canvas，用户拖动浏览器窗口时**不会自动适应**。  
必须监听 `resize` 事件手动调用。这是用 ECharts 最容易忽略、但一定会遇到的问题。

**③ 组件卸载时要清理**

```js
onUnmounted(() => {
  window.removeEventListener('resize', handleResize)
  pieChart && pieChart.dispose()
})
```

**有加必有减** —— 不清掉监听器，来回切标签页会累积无用监听，时间长了拖慢页面（内存泄漏）。

## 十二、错误对照表（Day8 新增）

| 现象                                                 | 原因                                        | 怎么办                                        |
| -------------------------------------------------- | ----------------------------------------- | ------------------------------------------ |
| 启动报 `Cannot find class: Xxx`（类明明存在）                | XML 简写别名，但该类所在包没配进 `type-aliases-package` | 加进配置（逗号分隔）或写完整包名                           |
| `SELECT category, amount ... GROUP BY category` 报错 | `SELECT` 里的非聚合列没在 `GROUP BY` 里            | 用聚合函数包起来，或加进 `GROUP BY`                    |
| 空月份的合计显示成 `¥ null` 或报错                             | `SUM` 对空集合返回 NULL                         | `IFNULL(SUM(...), 0)`                      |
| 图表区域一片空白                                           | 没数据时没画任何东西，用户不知道是"加载中"还是"没数据"             | 空数据时给文字提示                                  |
| 拖动窗口大小，图表不变形                                       | 没监听 `resize` 手动调用                         | 加 `window.addEventListener('resize', ...)` |
| 切标签页几次后页面变卡                                        | 监听器没清理、图表实例没销毁                            | `onUnmounted` 里 remove 和 dispose           |
| 统计结果某个字段全是 `null`                                  | SQL 别名和 vo 属性名对不上                         | 核对别名                                       |
| 月份传 `abc` 却显示"没有账单"                                | 没做格式校验，静默查不到                              | 用正则校验 `\d{4}-\d{2}`                        |

## 十四、一个数据小发现（要不要改，你决定）

统计收入分类时发现这条：

| id | 类型     | 金额     | 分类     | 日期         |
| -- | ------ | ------ | ------ | ---------- |
| 7  | **收入** | 100.01 | **餐饮** | 2026-10-10 |

**"餐饮"被记成了"收入"** —— 餐饮一般是花钱的，可能是你测试时类型选错了。

**这引出一个真实的业务问题**：一个分类既可以是支出也可以是收入（比如"餐饮"  
最可能是支出，但"其他"就可能两边都有），所以**我们现在没有强制校验**  
"餐饮不能是收入"。

**真实系统里怎么处理？** 通常给分类加一个"方向"属性：

```
餐饮    → 只允许支出
工资    → 只允许收入
其他    → 两者都行
```

这样在记账时就能自动过滤/校验。**这是个很好的练习题**，想不想下次做？

（现在不改，因为要动表结构 —— 加字段 + 数据迁移，是个完整的小课题。）
