## 二、主链：加上门卫之后

```
浏览器（带着 Authorization 头）
     ↓
★ AuthInterceptor.preHandle()      ← 今天新增的环节，在 Controller 之前
     ↓  检查通过 → 放行               检查不过 → 抛 UnauthorizedException
     ↓                                        ↓
DispatcherServlet → Controller        GlobalExceptionHandler
     ↓                                        ↓
Service → Mapper → MySQL              401 + {"code":1,"msg":"请先登录"}
```

**关键点：拦截器是"横切"的** —— 它不属于某一条业务链，而是横在所有业务的前面。

## 三、核心概念

### 概念 1：拦截器站在哪？和过滤器什么区别？

```
HTTP 请求
   ↓
① Filter（过滤器）      ← Servlet 层，比 Spring 更靠外，能碰到所有请求
   ↓
② DispatcherServlet     ← Spring MVC 的总调度
   ↓
③ Interceptor.preHandle ← 拦截器，在 Controller 之前   ← 今天用的
   ↓
④ Controller
   ↓
⑤ Interceptor.postHandle（Controller 正常返回后才执行）
   ↓
⑥ Interceptor.afterCompletion（无论成功失败，最后一定执行）
```

| | Filter（过滤器） | Interceptor（拦截器） |
|---|---|---|
| 属于哪一层 | Servlet 容器 | Spring MVC |
| 能拿到什么 | 只有 request/response | **还能拿到"即将执行哪个 Controller 方法"** |
| 用 Spring 的 Bean | 不方便 | 方便（可以直接注入 JwtUtil） |
| 典型用途 | 编码、跨域、请求日志 | **登录检查、权限检查** |

> 我们今天要读 token、要用 JwtUtil —— 所以选拦截器更顺手。

### 概念 2：`preHandle` 的返回值是"生死开关"

```java
public boolean preHandle(HttpServletRequest req, HttpServletResponse resp, Object handler)
```

| 返回 | 结果 |
|---|---|
| `true` | 放行，请求继续往下走到 Controller |
| `false` | **到此为止**，Controller 不会被调用 |

**但我们这里没有 `return false`，而是 `throw` 异常。为什么？**

因为如果 `return false`，就得自己用 `response.getWriter()` 手写一段 JSON 回去 ——
那样响应体的格式就要手写，容易跟别处不一致。

而**抛异常**会被 `@RestControllerAdvice` 接住，走跟业务错误**完全相同**的出口，
响应体自然就是 `{code, msg, data}` 的格式。

> **一个值得记住的结论**：拦截器里抛的异常，全局异常处理器接得住。
> 因为 DispatcherServlet 调用 preHandle 时是包在 try-catch 里的，
> 一旦抛异常，会走和 Controller 抛异常**一模一样**的流程。

### 概念 3：放行名单（白名单）—— 今天最容易想漏的地方

```java
registry.addInterceptor(authInterceptor)
        .addPathPatterns("/api/**")            // 要拦的范围
        .excludePathPatterns(                  // 放行名单
                "/api/user/register",
                "/api/user/login",
                "/api/ping"
        );
```

**为什么"登录"接口必须放行？**

> 因为你**登录之前手上还没有 token**。
> 如果登录接口也要求带 token，那你永远也登不进去 —— 这是死循环（鸡生蛋问题）。

**为什么 `/api/ping` 也要放行？**

> 它是探活接口，部署时监控系统会来请求它，那些请求当然不会带 token。
> 拦了它等于"医院门卫要求病人先挂完号才能进门挂号"。

**`/api/**` 里的两个星号是什么意思？**

| 写法 | 匹配范围 |
|---|---|
| `/api/*` | 只匹配**一层**，`/api/ping` ✓，`/api/user/me` ✗ |
| `/api/**` | 匹配**任意层级** ✓✓ |

**为什么不用手动排除前端页面？** 因为 `addPathPatterns("/api/**")` 已经限定了范围，
`/`、`/index.html`、Vite 资源那些路径不以 `/api` 开头，压根不在拦截范围内。
**"只拦该拦的"** —— 范围设太宽会连页面都打不开。

### 概念 4：规则表又长了一层（今天加的是第 0 层）

Day5/Day6 我们一起打磨过一张"什么时候用 401/404/400/200"的表。今天它变了：

```
┌──────────────────────────────────────────────────────────────┐
│ 第 0 层：身份层（连"你是谁"都不知道）                          │
│   · 没带 token / token 过期 / 签名被改    → 401  ← 今天新增    │
├──────────────────────────────────────────────────────────────┤
│ 第 1 层：HTTP 层（请求本身有毛病）                             │
│   · 地址不存在                            → 404                │
│   · 请求方法用错                          → 405                │
│   · 参数格式错 / 请求体格式错             → 400                │
├──────────────────────────────────────────────────────────────┤
│ 第 2 层：业务层（请求没毛病，只是规则不允许）                  │
│   · 账户名称为空 / 余额不足 / 记录不存在  → 200 + code≠0       │
└──────────────────────────────────────────────────────────────┘
```

**为什么"未登录"必须单独用 401？**

因为它让前端能写一处**统一逻辑**：

```js
if (status === 401) { 清掉 token; 跳回登录页 }
```

**不用去读 msg 里到底写了什么字。** 这就是标准状态码的价值 —— 让处理逻辑不依赖文案。
（如果哪天你把提示语从"请先登录"改成"登录状态已过期"，前端一行都不用改。）

### 概念 5：`@RequestAttribute` —— 取参数家族第 5 个成员

```
@PathVariable      从 URL 路径里取          /api/account/6
@RequestParam      从 URL 问号后取          ?month=2026-10
@RequestBody       从请求体里取             {"username":"xxx"}
@RequestHeader     从请求头里取             Authorization: Bearer xxx
@RequestAttribute  从 request 的属性里取    ← 今天这个
```

**第五个和前面四个有本质区别，这是今天最该记牢的一点：**

| | 值的来源 | 能不能信任 |
|---|---|---|
| 前四个 | **客户端发来的** | ❌ 用户想改就能改 |
| 第五个 | **服务器自己放进去的** | ✅ 可以信任 |

拦截器里干的：
```java
request.setAttribute("userId", 1L);   // 验签通过后才放进去
```
Controller 里取：
```java
public Result<?> me(@RequestAttribute("userId") Long userId)
```

**为什么这个区别是生死攸关的？**

如果这里是从请求里让客户端传的（比如 `/me?userId=2`），
那用户把 2 一改，就能看别人的数据 —— 这叫**水平越权**，
是 Web 系统里最常见、危害最大的一类漏洞。

> **一句话**：凡是从客户端来的东西都要怀疑，凡是服务器自己产生的才可以信。
> （这跟 Day4 讲的"前端校验不可信"是同一条原则的两个面。）

### 概念 6：认证 vs 授权（今天只做了前者）

| | 英文 | 回答什么问题 | 今天的状态 |
|---|---|---|---|
| **认证** | Authentication | **你是谁**？ | ✅ 做完了 |
| **授权** | Authorization | **你能不能动这条数据**？ | ❌ 明天做 |

```
现在的情况：
  张三登录了（认证 ✓），但 account 表里**没有 user_id 这一列**，
  所以他虽然登了录，看到的仍然是**所有人的**账户和账单。

  Day11 要做：
    · account / bill 加 user_id
    · 查询时带上 WHERE user_id = #{当前登录用户}
    · 插入时自动填上当前用户的 id（不许客户端自己传）
```

**拦截器只能证明"你是个合法用户"，它没法知道"第 8 号账单是不是你的"** ——
因为那需要业务知识（账单属于谁），而拦截器不认识业务。所以必须分两层做。

## 四、前端：一对"孪生"拦截器

后端有拦截器，前端也有。今天两边各配了一个，方向相反：

```
浏览器                    网络                   服务器
   │
   ├─ 前端请求拦截器     ── 出门前自动带上通行证 ──→
   │   （自动加 Authorization 头）
   │
   │                                          ├─ 后端拦截器 preHandle
   │                                          │   （进门时查证）
   │
   ├─ 前端响应拦截器     ←── 收到 401 统一处理 ──
   │   （清 token + 回登录页）
   ▼
```

### 前端请求拦截器：一处改动，全局生效

```js
request.interceptors.request.use((config) => {
  const token = getToken()
  if (token) config.headers.Authorization = 'Bearer ' + token
  return config
})
```

**为什么必须抽成一个统一模块？**

今天之前，`App.vue` 里有 7 处 axios 调用、`StatsPanel.vue` 里有 4 处。
如果不抽出统一模块，就得改 11 处，而且**以后新加的请求一定会有人漏写** ——
漏写的那个请求会莫名 401，还很难查是哪儿漏的。

抽出来之后：**加一次 token 逻辑，11 个请求全部生效，以后新增的也自动生效。**

### 前端响应拦截器：401 的归宿

```js
request.interceptors.response.use(
  (response) => response,
  (error) => {
    if (error.response?.status === 401) {
      clearAuth()
      ElMessage.warning('登录已失效，请重新登录')
      window.location.reload()     // 回到最干净的状态
    }
    return Promise.reject(error)
  }
)
```

**两个设计点：**

**① 为什么要 `location.reload()` 而不是手动切界面？**
因为 reload 让整个应用回到**最干净的状态**：内存里那些列表数据全部清空，
`App.vue` 重新挂载时一看 localStorage 没 token，自然就显示登录页了。
比手动清各种变量更可靠、更不容易漏。

**② 为什么要一个 `handling401` 标志位？**
因为页面加载时可能**同时**发好几个请求（我们统计页就并发 4 个）。
token 一过期，4 个请求同时返回 401 → 就会弹 4 个提示、刷新 4 次。
一个布尔标志就能保证只处理第一次。

> **这类"并发导致重复处理"的问题很常见**，值得记一笔。

### 前端的"路由守卫"其实就是一行 v-if

```vue
<LoginPanel v-if="!loggedIn" @success="handleLoginSuccess" />
<div v-else class="page"> ...主界面... </div>
```

真实项目里通常用 `vue-router` 的全局前置守卫实现，**但原理就是这个**：
"没有登录凭证，就不让看主界面"。

`loggedIn` 的判断依据是 **localStorage 里有没有 token**，
而不是一个普通的 `ref(false)` —— 因为 ref 的值刷新页面就没了，
用户一按 F5 就得重新登录。

## 六、今天我自己踩的坑（两个，都是真实的）

### 坑 1：测试用户名超长，但被 catch 吞掉了（差点白查一小时）

拦截器测试第一次跑就红了：

```
java.lang.IllegalArgumentException: 用户名或密码错误
```

**真正的第一现场其实在更早的地方**：我起的用户名 `interceptor_test_user`
是 **21 个字符**，而规则是"3-20 位" → **注册那一步就被校验拦下了**。

**但我的 `catch` 把所有 `IllegalArgumentException` 都当成"用户名已存在"忽略掉了**，
于是真正的错误被悄悄吞掉，等到登录时才报出一个**完全不相干**的错误信息。

**两条经验：**

> ① **catch 要"精确"**：只吞你预期的那一种失败，别的一律往上抛。
> 否则异常被吃掉，现场彻底丢失，你会沿着错误的方向查很久。
>
> ② **别被后续的连锁错误带偏**：报出来的错，未必是**最先**出错的地方。
> 往下追一层，往往能找到"第一现场"。

### 坑 2：测试每跑一次，就往数据库里扔一个垃圾账号

Day9 我写的测试用 `"junit_" + 时间戳` 生成用户名，本意是避免重名。
结果今天一看数据库：

```
| 4 | junit_3441164 | 自动化测试用户 |
| 6 | junit_3495751 | 自动化测试用户 |
```

**每跑一次测试就留一个永久垃圾账号。**

**正确做法：测试要自己收拾现场。**

```java
@BeforeEach
void 清掉可能残留的测试账号() {
    jdbcTemplate.update("DELETE FROM `user` WHERE username = ?", NAME);
}

@AfterEach
void 收拾现场() {
    jdbcTemplate.update("DELETE FROM `user` WHERE username = ?", NAME);
}
```

跑之前清、跑完清，所以测试**可以无限次重复执行，数据库始终干净** ——
这叫**测试的幂等性**，是自动化测试的基本要求。

> **顺带一个副产品**：加了 `@BeforeEach` 清理之后，`catch` 就不需要了
> （注册必然成功）。这也印证了一句话：
> **很多时候"写 catch 兜住"不是解法，把前面的状态弄干净才是。**

## 七、常见错误对照表

| 现象 | 原因 | 怎么办 |
|---|---|---|
| 登录接口也返回 401，永远登不进去 | 放行名单里漏了 `/api/user/login` | 加进 `excludePathPatterns` |
| 前端页面本身打不开（401） | `addPathPatterns` 写太宽，比如写成了 `/**` | 限定成 `/api/**` |
| 前端所有请求都 401 | 忘了加 `Bearer ` 前缀，或没走统一的 request | 检查 axios 请求拦截器 |
| `/me` 报 400 说参数缺失 | `@RequestAttribute("userId")` 的名字跟 `setAttribute` 的对不上 | 用**常量**统一名字，别手写两遍字符串 |
| 接口莫名 401，但明明带了 token | 前端某处还在直接 `import axios` 绕过统一模块 | 全局搜 `from 'axios'`，只允许出现在 `api/request.js` |
| 后端重启后所有用户都要重新登录 | 服务器重启时换了 JWT 密钥 | 密钥要固定（放配置文件/环境变量），不能每次随机生成 |
| 401 后页面反复刷新 | 多个请求同时 401，都被处理了 | 用标志位只处理第一次 |
| 跨域场景下预检请求被拦 | OPTIONS 请求不会带 Authorization | 拦截器里先放行 OPTIONS |

## 八、排错套路（今天新增一条）

前面已有的套路：
- 读报错原话 → 找多条报错的共同根因 → 逐层验证
- "找不到东西 / 连不上 / 版本不对"三分类
- 用 `curl` 逐层测（测后端、测代理）

**今天新增：权限类问题的排查顺序 —— 从外往里剥**

```
① 用户手上到底有没有 token？
     → 浏览器 F12 → Application → Local Storage 看一眼

② 请求有没有把它带上？
     → F12 → Network → 点那个请求 → Headers → 看有没有 Authorization

③ 带上了，后端认不认？
     → 看后端日志里是"请先登录"还是"登录已失效"
        有人说没带  → 问题在①或②（前端）
        说失效了    → token 本身有问题（过期 / 密钥换了 / 被改过）

④ 后端认了，业务有没有放行？
     → 看是不是 403（权限不够）而不是 401（没登录）
```

> **核心思路：一层一层往里剥，每一层只问一个是非题。**
> 别一上来就"可能是 token 的问题"，那样猜不出来。

## 九、诚实的提醒：现在还缺什么

**一句话总结今天的成果与局限：**

> **今天证明了"你是你"，但还没证明"这东西是你的"。**

张三打开账单页  → 看到的是【所有人】的账单 ✗
张三点删除      → 能把李四的账户删掉 ✗

因为整个 `account` / `bill` 表里**根本没有"属于谁"这个信息**。

**Day11（数据隔离）要做三件事：**

2. **查询带上条件**：`WHERE user_id = #{当前登录用户}`

   （—— 又回到今天那个知识点：客户端来的都不能信）

**顺便会碰到的两个新问题：**

## ⚠️ 事故复盘：页面无限刷新（Day10 上线当天的真实事故）

> 这一节是**当天修完 bug 后补记的**，是一个完整的"故障 → 定位 → 修复 → 验证"实录。
> 它比上面任何一节都更接近真实工作。

### 现象

用户打开 `http://localhost:5173`，**页面疯狂刷新，根本来不及输入账号密码**。

### 定位：用日志取证，不靠猜

我做的第一件事**不是看代码，而是看后端日志** —— 因为如果页面在循环，后端一定会留下痕迹。

```
19:11:06.848  ← 一对
19:11:07.021
19:11:08.003  ← 又一对（隔 0.98 秒）
19:11:08.007
19:11:08.854  ← 又一对（隔 0.85 秒）
19:11:08.861
19:11:09.703  ← 又一对
19:11:09.711
```

**两条线索直接锁定了根因：**

| 线索 | 说明 |
|---|---|
| **成对出现** | 每次页面加载正好发 **2 个请求** → 对应 `onMounted` 里的 `loadAccounts()` + `loadBills()` |
| **每轮间隔约 0.85 秒** | 对应代码里的 `setTimeout(() => location.reload(), 800)` |

两条一对上，循环链路就出来了。

### 根因：`onMounted` 忘了判断"有没有登录"

`App.vue`：

```js
onMounted(async () => {
  await loadAccounts()   // ← 不管有没有登录都会执行
  await loadBills()
})
```

完整链路：

```
页面加载（还没有 token）
  → 渲染出登录页 ✓
  → 但 onMounted 照样发 loadAccounts / loadBills
  → 后端返回 401（Day10 拦截器上线了，没证不让进）
  → 前端响应拦截器 clearAuth + location.reload()
  → 页面重载 → 又发请求 → 又 401 → 又刷新 …… ∞
```

> **注意这个 bug 的性质**：它不是"某一行写错了"，而是
> **两个各自都正确的改动，组合起来产生了副作用**。
> Day10 单独加 `onMounted` 时没问题（那时 401 不触发跳转）；
> 单独加"401 自动跳登录"时也没问题。**它们碰到一起才出问题。**
> 这类 bug 最难查，因为每一处代码单看都是对的。

### 修复：三层防护

**第一层（根因）：从源头不发请求**

```js
onMounted(async () => {
  if (!loggedIn.value) return     // ← 这一行是关键
  await loadAccounts()
  await loadBills()
})
```

**第二层：拦截器只处理"该它管"的情况**

```js
if (status === 401) {
  if (!getToken()) {
    // 手上本来就没证 —— 说明是"未登录就调了需要登录的接口"，
    // 这是前端**调用时机**的问题，刷新解决不了，只会变成死循环
    return Promise.reject(error)
  }
  // ...手上有证但失效了，这才该清证 + 回登录页
}
```

> **拦截器不该负责修补调用方的错误**，只该处理"凭证失效"这一种情况。

**第三层：自动刷新最多只做一次**

```js
if (sessionStorage.getItem(RELOAD_FLAG)) {
  ElMessage.error('登录状态异常，请关闭页面重新打开')
  return Promise.reject(error)     // 不再刷新
}
sessionStorage.setItem(RELOAD_FLAG, '1')
```

登录成功或请求成功时清掉这个标记，恢复成"还能再救一次"。

### 验证：用无头浏览器实测（不靠"应该没问题了"）

因为**没法靠肉眼看**"页面有没有在循环"，我用你机器上的 Edge 做了两次无人加载：

| 实验 | 做法 | 结果 |
|---|---|---|
| **A. 全新访客** | 无任何历史数据打开页面 | 401 数量 **8 → 8（零新增）**，DOM 里出现「注册新账号」→ **停在登录页** ✅ |
| **B. 带坏 token** | 往 localStorage 塞一个假 token 再打开 | 401 只多了 **6 条，且全部挤在 25 毫秒内**（一次加载发 6 个请求：账户 1 + 账单 1 + 统计 4）→ 去重成一次刷新后停住 ✅ |

**为什么"25 毫秒内 6 条"能证明没有循环？**
因为循环的特征是**有间隔地反复出现**（像上面 0.85 秒一轮那样）。
全部挤在一瞬间 = 同一批并发请求 = 只加载了一次。

> **这是排查"是不是死循环"的一个通用判据：看时间戳的分布。**
> 有规律的间隔 → 循环；一次性爆发 → 单次触发。

### 从这次事故带走的四条经验

1. **加了"全局自动跳转"之后，必须回头检查所有会自动发请求的地方**
   （`onMounted`、`watch`、定时器、轮询……）—— 它们都会触发那个自动跳转。
2. **"自动重试 / 自动跳转 / 自动刷新"必须配次数上限**。一旦触发条件没被真正消除，行为就会无限重复。
3. **判断要写在发请求之前**，而不是等收到 401 再补救。从源头不发，比发出去再拦更简单可靠。
4. **报bug时先取证，再改代码。** 这次的日志时间戳（成对 + 0.85 秒间隔）三步就锁定了根因，
   比漫无目的地读代码快得多。

### 顺带发现的一个小浪费

`el-tabs` 默认会**把所有标签页内容都渲染出来**（只是隐藏），所以主界面一加载，
统计组件 `StatsPanel` 也会挂载并发 4 个请求 —— 哪怕用户还停在「账户」标签页。

不致命，但可以优化：给 `el-tabs` 加 `lazy`，让标签页**第一次被点开时才加载**。
记在这里，以后优化性能时可以用。
