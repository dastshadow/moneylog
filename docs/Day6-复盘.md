## 二、你的表设计好在哪（这一节值得反复看）

我看了你写的建表语句，**有 5 个决策做得很到位**：

| # | 你的设计 | 好在哪 |
|---|---|---|
| 1 | **加了外键约束**<br/>`FOREIGN KEY (account_id) REFERENCES account(id)` | 数据库层面**保证不会有"孤儿账单"**——你没法给不存在的账户记账 |
| 2 | **加了两个索引**<br/>`idx_account_id`、`idx_bill_date` | 为"按账户查""按日期查"提前铺好路。账单表数据会越攒越多，索引就是提前买好的"加速卡" |
| 3 | **`type` 用 tinyint（1=支出，2=收入）** | 比存中文字符串省空间、也不容易写错（"支出"写成"支岀"就出问题了） |
| 4 | **`amount` 存正数，方向由 `type` 决定** | 比"支出存负数"清晰得多。任何地方看金额永远是正的，方向看 type，不会搞混 |
| 5 | **`bill_date`（日期）和 `created_at`（录入时间）分开** | ⭐ **最有价值的一条**（下面单独说） |

### 第 5 条为什么最有价值

```
bill_date   = 哪一天的钱        （DATE，只有年月日）
created_at  = 什么时候记的这笔账 （DATETIME，含时分秒）
```

**场景**：你昨天打车花了 25 块，今天才想起来补记。

- `bill_date` 填**昨天**（这笔钱是昨天花的）
- `created_at` 是**今天**（数据库自动盖的时间戳）

**如果只有一个时间字段，这个需求就满足不了**，而且"按月份统计开支"会算错
—— 补记的账会被算到补记那天。

**很多工作两三年的人都想不到要把这两个分开**，你第一次建表就分开了。

## 三、外键：为什么账单存"编号"而不是"账户名字"

这是今天最重要的概念。看图：

```
account 表                    bill 表
  id=1 微信钱包    ←──────    account_id=1
  id=2 支付宝                    amount=35.00
  id=6 中国银行                  category=餐饮
```

**为什么 bill 表里存 `account_id = 1`，而不是直接存 "微信钱包"？**

因为存名字有两个大问题：

| 问题 | 具体后果 |
|---|---|
| **改名的代价** | 账户改名成"微信零钱"后，几百条旧账单还写着"微信钱包"，得逐条改，**还可能改漏** |
| **写错的风险** | 可能把"微信钱包"写成"微信钱宝"，于是**同一个账户在账单里变成了两个** |

**存编号的好处**：名字只在 `account` 表里存**一份**。改名只改一处，所有账单**自动跟着变**。

**代价**：想看名字要"连表查询"把两张表接起来 —— 这就是今天学的 JOIN。

### 外键约束的额外作用

`FOREIGN KEY` 不只是"说明关系"，它是**数据库真的会强制执行**的规则：

> 你往 bill 表插一条 `account_id = 999`（不存在）的记录，**MySQL 会直接拒绝**。

这是数据库帮你守的一道门。**但我们的 Service 里还自己查了一遍**，为什么？

| 做法 | 效果 |
|---|---|
| 只靠数据库外键 | 数据一定正确，但报错是底层 SQL 异常，用户看到"系统繁忙" |
| **Service 里先查**（我们做的） | 能给出"所选账户不存在，请重新选择"这种人话提示 |

**这跟 Day4 讲的"前端校验 vs 后端校验"是同一个道理**：

> 数据库外键 = 最后一道防线（一定拦得住，但提示不友好）
> Service 校验 = 友善的拦截（给用户人话）
> **两道都要有**：前者保证数据绝对正确，后者保证体验良好。

## 四、连表查询（JOIN）—— 今天的重头戏

### 问题

`bill` 表里只有 `account_id = 1` 这个数字，但页面上要显示"微信钱包"。
只查一张表拿不到名字。

### 解决

```sql
SELECT b.id, b.account_id, b.type, b.amount, b.category,
       b.bill_date, b.remark, b.created_at,
       a.name AS account_name           ← 关键的一列
FROM bill b                              ← b 是 bill 的小名（别名）
LEFT JOIN account a ON b.account_id = a.id    ← 把两张表接起来
ORDER BY b.bill_date DESC, b.id DESC
```

### 逐段拆解

**① `bill b` / `account a` —— 表别名**

给表起个简称，后面就不用反复写完整表名。
而且**两张表都有 `id` 和 `name` 字段**，必须用 `b.id` 和 `a.id` 区分开，
否则 SQL 会报"字段名有歧义"。

**② `ON b.account_id = a.id` —— 连接条件（JOIN 的核心）**

翻译成人话：

> "把 bill 表里每一行的 `account_id`，去 account 表里找 `id` 相同的那些行，配成一对。"

配上的部分**拼成一行**，就能同时看到账单信息和账户名称了。

这个连接条件用的正是**你建表时定义的那条外键关系**。

**③ 为什么用 `LEFT JOIN` 而不是 `JOIN`？**

| 写法 | 行为 |
|---|---|
| `JOIN`（内连接） | 只保留"两边都配得上"的行。**配不上的行直接消失** |
| `LEFT JOIN`（左连接） | 保留**左表（bill）的所有行**。右表配不上时字段给 `null`，但行还在 |

**这里必须用 LEFT JOIN**，原因很重要：

> 如果用内连接，万一某条账单的账户被删了，
> 这条账单会在列表里**凭空消失** —— 用户明明记过一笔账，却找不到了，还没有任何提示。

**这种"数据静默丢失"是最难排查的一类问题。**

用 LEFT JOIN，账单一定还在，只是账户名显示为空，我们能在页面上标出来。

> **一句话记住**：`LEFT JOIN` 更"保守"，**宁可多留一行空着的，也不悄悄弄丢数据**。
> 所以它是大多数业务查询的默认选择。

**④ 结果怎么变成 Java 对象的？**

SQL 查出来的列名是 `account_name`（下划线），Java 字段是 `accountName`（驼峰）。
能自动对应上，靠的还是 Day1 配的那行：

```yaml
map-underscore-to-camel-case: true
```

**这个配置今天在连表查询里又用上了** —— 基础设施的价值就是这样，配一次，后面一直受益。

**⑤ `ORDER BY b.bill_date DESC, b.id DESC`**

账单日期倒序（新的在上）；日期相同的，按 id 倒序（后记的在上）。
记账应用都是"最近的账在最上面"，符合直觉。

（`DESC` = 降序；`ASC` = 升序，是默认值，可以不写）

## 五、一个容易忽略的认知：实体类可以有"表里没有的字段"

看 `Bill.java` 最后那个字段：

```java
/** 【表里没有这一列】连表查询带回来的账户名称，仅用于显示 */
private String accountName;
```

**`bill` 表里根本没有 `account_name` 这一列**，但 Java 对象里有这个属性。

**这完全允许，而且很常见。**

**为什么需要它？** 因为要让前端直接显示"微信钱包"，而不是干巴巴的"1"。
我们在查询时把账户名一起查出来，塞进这个字段，问题就解决了。

**注意区分**：
- 表里有、对象里也有 → 正常字段（id、amount、category…）
- 表里没有、对象里有 → **查询时"顺便带回来"的字段**（accountName）
- 新增时这个字段**不用传**，数据库也不关心它（回看 `BillMapper.xml` 的 INSERT，没有它）

> 所以"实体类必须和表一一对应"是个**误解**。它们大部分时候对应，但不强求。

## 六、今天撞到的坑：同类问题第二次出现（很有价值）

**做账单时我试了一下日期用斜杠格式**：

```
POST /api/bill/create
{"billDate":"2026/10/10"}        ← 用了斜杠
```

**结果**（修复前）：
```
HTTP 200 + {"code":1,"msg":"系统繁忙，请稍后再试"}     ← 提示错了
日志：ERROR ... 系统异常
      HttpMessageNotReadableException: JSON parse error:
      Cannot deserialize value of type `java.time.LocalDate`
      from String "2026/10/10"
```

### 这和 Day5 是**同一类问题的翻版**

Day5 遇到的是"URL 参数类型转换失败"（`/api/account/abc`），
今天遇到的是"请求体日期格式解析失败"，**三个毛病一模一样**：

| 毛病 | Day5 | Day6 |
|---|---|---|
| 提示错 | "系统繁忙" | "系统繁忙" |
| 日志级别错 | ERROR | ERROR |
| 状态码错 | 200 | 200 |

### 从这件事能提炼出的重要认知

Day5 修完参数类型错之后，我以为"该修的异常都修完了"。
结果今天一换数据类型（`LocalDate`），同样的坑又出现一次。

> **所以：兜底方法（`@ExceptionHandler(Exception.class)`）是"垃圾桶"，
> 它不是解决方案，只是最后一道保险。**
>
> 每当你发现某类异常**经常出现、且有明确含义**，
> 就该把它从垃圾桶里捞出来，单独配一个处理方法。

**推论**：全局异常处理器会随着项目推进**不断变长 —— 这是健康的演进，不是设计缺陷。**
真实项目里的全局异常处理器往往有十几个方法。

### 顺便：我把规则统一了

修今天这个问题时，回头检查发现 Day5 有个**不一致**：

| 情况 | 当时给的 |
|---|---|
| 404 找不到地址 | 真实状态码 ✓ |
| 参数类型转换失败 | **200** ✗ 不一致 |

两者其实是**同一类问题**（都是"请求本身有毛病"），所以我把它们统一了：

```
┌──────────────────────────────────────────────────┐
│  HTTP 层面的问题（请求本身有毛病）                 │
│    · 地址不存在          → 404                    │
│    · 请求方法用错        → 405（Spring 默认）      │
│    · 路径参数类型不对    → 400   ← 本次调整        │
│    · 请求体格式不对      → 400   ← 今天新增        │
├──────────────────────────────────────────────────┤
│  业务层面的问题（请求没问题，只是规则不允许）      │
│    · 账户名称为空        → 200 + code=1            │
│    · 记录不存在          → 200 + code=1            │
│    · 金额为负数          → 200 + code=1            │
└──────────────────────────────────────────────────┘
```

**一句话：**
> **"请求有毛病"用 4xx；"业务被拒绝"用 200 + code。**

**为什么要这样分？**
- 前者是**调用方把请求写错了** → 用 4xx，让监控系统能统计出来
- 后者是**业务上不允许**，是正常的业务失败 → 用 200，因为这次网络交互本身是成功的

> 💡 **"设计规则"这件事，很少一次就做对。** 今天是第 6 天，
> 我们已经回头修了 3 次异常处理规则。这很正常 ——
> **真实项目里，规范是在不断遇到反例的过程中打磨出来的。**

## 七、几个今天新出现的小知识点

### 1. `LocalDate` vs `LocalDateTime` 对应 DATE vs DATETIME

| 数据库类型 | Java 类型 | 含义 |
|---|---|---|
| `DATE` | **`LocalDate`** | 只有年月日（2026-10-10） |
| `DATETIME` | **`LocalDateTime`** | 年月日 + 时分秒（2026-10-10 20:30:14） |

**选哪个由业务决定**：账单日期只需要"哪一天"，所以用 DATE；录入时间要精确到秒，所以用 DATETIME。

### 2. 前后端的日期格式约定

Jackson（负责 JSON 转换的库）**默认只认国际标准格式**：

```
"2026-10-10"   ← 短横线 ✓
"2026/10/10"   ← 斜杠   ✗ 会报错
```

所以前端 `el-date-picker` 必须加这个设置：

```vue
<el-date-picker value-format="YYYY-MM-DD" />
```

**它会决定选择器交出来的字符串长什么样。** 写成 `YYYY/MM/DD` 就会触发上面那个错误。

> 这就是"前后端约定"的一个具体例子：**接口文档里必须写明日期格式**，
> 否则两边各写各的，就会撞车。

### 3. "魔法数字"要变成常量

```java
// ❌ 不好：半年后自己看都愣一下"1 是啥？"
if (type == 1) { ... }

// ✅ 好：一眼就懂
if (type == Bill.TYPE_EXPENSE) { ... }
```

在 `Bill.java` 里定义：
```java
public static final int TYPE_EXPENSE = 1;
public static final int TYPE_INCOME = 2;
```

**直接写在代码里的数字叫"魔法数字"** —— 它的含义只存在于写代码那个人的脑子里。
用常量既能自解释，以后要改含义也只改一处。

### 4. 判断数字大小的固定套路：先判 null，再比数值

```java
if (bill.getAmount() == null || bill.getAmount().compareTo(BigDecimal.ZERO) <= 0) {
```

**为什么要先判 null？** 因为 `null.compareTo(...)` 会直接崩溃（空指针异常）。

**这是所有比较操作的固定套路**：
> **先用 `== null` 兜住，再做数值比较。**

（`||` 是"或"，而且它有个好特性叫"短路"：前面条件为真时，后面根本不会执行。
所以 `null` 的判断放在前面，后面那句 `compareTo` 就安全了。）

## 九、错误对照表（Day6 新增）

| 现象 | 原因 | 怎么办 |
|---|---|---|
| 日期传 `"2026/10/10"` 报"格式不正确" | Jackson 只认短横线格式 | 前端设 `value-format="YYYY-MM-DD"` |
| 账单列表里"账户"列是空的 | 用了 `JOIN` 而不是 `LEFT JOIN`，或该账户已被删 | 检查 JOIN 类型 |
| 加账单报"所选账户不存在" | `accountId` 传了不存在的编号 | 检查前端下拉框取的是不是真实账户 id |
| 列表里账户显示 `1` 而不是名字 | SQL 里没写 `a.name AS account_name` | 检查 SELECT 的列 |
| 账单看不到"账户名"字段 | 忘了开驼峰映射 | 检查 `application-config` 的 `map-underscore-to-camel-case` |
| `<el-radio>` 用了 `label` 不生效 | 2.6 版本后推荐用 `value` | 改用 `:value="1"`（旧版本才用 `label`） |
| 账单日期总差一天 | 用 `toISOString()` 后有时区问题 | 手动按年月日拼字符串 |

## 十二、明天预告（Day7）

**今天留了一个"缺一块"的地方，你发现了吗？**

现在记一笔账，**账单表会多一条，但账户余额完全没变。**

```
在"微信钱包"记一笔 35 元的餐饮支出
→ bill 表多了一条 ✓
→ 但微信钱包的余额还是 1000.00，应该变成 965.00 ✗
```

**为什么？因为"记账"这件事其实要同时做两个动作：**
1. 往 `bill` 表插一条记录
2. 把 `account` 表的余额扣掉 35

**问题来了**：万一第 1 步成功了、第 2 步失败了，会怎样？
→ 数据库里就出现了一笔"付了钱但余额没扣"的账，**账就不平了**。

**解决这个问题的技术叫「事务」（`@Transactional`）。**

Day7 要学：
- **事务**：让多个数据库操作"要么全成功，要么全失败"（这是后端最重要的概念之一）
- **`UPDATE account SET balance = balance - ?`** —— 在数据库里做加减，而不是先查出来再算
- 演示"故意让第 2 步失败"，亲眼看到事务怎么把第 1 步也撤销掉

**今天是第一次遇到"需要保证多步操作一致性"的场景** ——
这也标志着项目从"简单 CRUD"进入了"真正的业务逻辑"。
